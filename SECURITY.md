1. Purpose

The security of this project and its users is important.

This Security Policy explains how security vulnerabilities affecting this project should be responsibly reported and how such reports may be handled.

This policy applies to security vulnerabilities discovered in the project's website, source code, scripts, configurations, and other original project components maintained by:

Balamurugan Dhandapani (Balamurugan D)

2. Supported Versions

Security fixes and maintenance are provided for the currently maintained version of the project.

Version	Supported
2026.x	:white_check_mark:
Older versions	:x:

Because this project is maintained as a continuously updated website rather than as a conventional software release with fixed versions, the latest publicly maintained version should be considered the primary supported version.

3. Reporting a Security Vulnerability

If you discover a potential security vulnerability, security weakness, accidental exposure of sensitive information, or other security-related issue affecting this project, please report it privately to the project owner.

Do not publicly disclose the vulnerability before it has been reviewed.

Where GitHub is used for project management, security vulnerabilities should preferably be reported through GitHub's private security vulnerability reporting mechanism, where available.

If private reporting is not available, contact the project owner using the contact information provided in the project's official repository or website.

4. Information to Include

To help investigate the issue, please provide as much of the following information as reasonably possible:

A clear description of the vulnerability;
The affected page, feature, file, or component;
Steps required to reproduce the issue;
The expected behavior;
The actual behavior;
Screenshots or recordings, where appropriate;
Relevant error messages;
The affected version or commit, if known;
The potential security impact;
A suggested remediation, if available.

Please do not include passwords, private credentials, authentication tokens, API secrets, personal information, or other sensitive data in the report unless absolutely necessary.

5. Responsible Disclosure

Security researchers and users are requested to provide a reasonable opportunity for the issue to be investigated and addressed before publicly disclosing technical details.

Please avoid:

Publicly posting unpatched vulnerabilities;
Publishing exploit code against the live website;
Accessing, modifying, deleting, or downloading data that does not belong to you;
Attempting to obtain unauthorized access;
Performing denial-of-service or destructive testing;
Social engineering of the project owner or users;
Attacking third-party services connected to the project.

Security testing should be limited to activity necessary to demonstrate the vulnerability without causing harm.

6. What Happens After a Report

After receiving a vulnerability report, the project owner will make reasonable efforts to:

Acknowledge receipt of the report;
Review and investigate the reported issue;
Determine whether the issue represents a genuine security vulnerability;
Assess its severity and potential impact;
Take reasonable steps to remediate confirmed vulnerabilities;
Provide updates where reasonably possible;
Deploy an appropriate fix or mitigation when feasible.

Response times may vary depending on the severity, complexity, and availability of the project maintainer.

7. Vulnerability Classification

Reported vulnerabilities may be classified according to their potential impact.

Examples include:

Severity	Description
Critical	Vulnerabilities that could result in severe compromise, unauthorized access, or significant damage
High	Vulnerabilities that could cause substantial security impact
Medium	Vulnerabilities with a meaningful but limited security impact
Low	Vulnerabilities with limited security consequences
Informational	Security observations that do not represent a significant vulnerability

The final severity classification will be determined by the project owner based on the circumstances and potential impact.

8. Accepted Vulnerabilities

If a reported issue is confirmed as a security vulnerability, the project owner may:

Develop and deploy a security fix;
Apply a temporary mitigation;
Update affected dependencies;
Change security configurations;
Remove or replace vulnerable functionality;
Document the issue and remediation where appropriate.

The project owner may determine the appropriate remediation based on the severity and practical impact of the vulnerability.

9. Declined Reports

A report may be determined not to constitute a security vulnerability.

Examples may include:

Issues that do not create a meaningful security risk;
Reports concerning intended website behavior;
Issues affecting only unsupported versions;
Vulnerabilities requiring unrealistic or unauthorized assumptions;
Third-party vulnerabilities outside the project's control;
Issues already known to the project owner;
General feature requests or usability issues.

Where reasonably possible, the reporter may be informed when a report is determined not to require security remediation.

10. Third-Party Services

This project may use third-party services, libraries, frameworks, APIs, hosting providers, fonts, scripts, or other external resources.

Security vulnerabilities that exist exclusively within third-party systems should generally be reported to the relevant third-party provider.

The project owner does not claim responsibility for vulnerabilities entirely outside the project's control.

11. Sensitive Information

If a security issue involves potentially exposed credentials, API keys, authentication information, personal information, or other sensitive information, please report it privately and avoid publicly disclosing the information.

If you accidentally discover a secret or credential, do not attempt to use it.

Report the exposure privately so that appropriate protective action can be considered.

12. Security Testing

Security testing of this project must be conducted responsibly.

Researchers should avoid actions that may:

Damage the website;
Disrupt availability;
Access another person's information;
Modify or delete data;
Circumvent authentication for unauthorized purposes;
Interfere with third-party infrastructure;
Create excessive traffic;
Degrade service for legitimate users.

Proof-of-concept testing should use the minimum level of activity necessary to demonstrate the reported issue.

13. Public Disclosure

The project owner may publicly disclose information about resolved security vulnerabilities when appropriate.

Any public disclosure may include:

Affected component;
General description of the vulnerability;
Severity;
Remediation;
Affected version;
Fixed version or commit;
Security acknowledgment, where appropriate.

Sensitive information and exploit details that could facilitate abuse may be withheld.

14. Researcher Recognition

Where appropriate and with the researcher's consent, the project owner may acknowledge security researchers who responsibly report valid vulnerabilities.

Researchers should indicate whether they wish to receive public acknowledgment.

No researcher should assume that public recognition, payment, employment, or any other compensation will be provided unless expressly agreed in writing.
